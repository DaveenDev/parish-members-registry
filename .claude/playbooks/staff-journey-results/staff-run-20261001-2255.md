## Restricted-staff friction observations

### P1
No P1 friction found.

### P2
- **f2-login-blank** — Submitting the staff sign-in form empty shows Supabase's raw text "missing email or phone". It mentions a phone, which this app does not use.
  → Suggestion: validate blank fields in `AdminLogin.jsx` and show "Enter your email and password."
- **f2-pw-blank** — With all three change-password fields blank the message is "New password must be at least 10 characters"; an empty *current* password is never called out.
  → Suggestion: check the current-password field first in `ChangePasswordCard` (`client/src/pages/admin/ParishConfig.jsx`).
- **f2-pw errors, accessibility** — The change-password error is a plain `div` with no `role="alert"`, unlike the sign-in form's error, so a screen reader will not announce it.
  → Suggestion: add `role="alert"` to that error element in `ChangePasswordCard`.
- **s-deeplink-lands-on** — Signing in after being sent from a deep link (e.g. `/admin/members`) always lands on `/admin`, not the requested page (docs/beta-testing AA-16 already treats this as S4).
  → Suggestion: pass the original path through `RequireAuth` and navigate back to it after sign-in.
- **s-p1-admin-unknown** — A mistyped `/admin/...` URL falls through to the catch-all and sends a signed-in staff member to the *public* home page.
  → Suggestion: add an `/admin/*` route that shows "page not found" inside the admin shell, or redirects to `/admin`.
- **d-session-window** — A disabled account keeps working until its access token expires (up to an hour); confirmed with a write using the old token. The disable dialog already warns about this.
  → Suggestion (optional): shorten the JWT expiry in Supabase Auth settings if an hour is too long for the parish.
- **s-cfg-identity** — A non-admin staff member can change the parish name, logo and contact details. This matches the documented design (every staff account can change all records) and is recorded as correct, not a bug.
  → Suggestion (optional): if the parish wants only staff admins to edit parish identity, gate `ProfileTab` on `user.isAdmin` and add an RLS policy on `parish_settings`.

- **H1 — a-rpc-create-hh / a-rpc-rename-gkk / a-rpc-delete-gkk** — Symptom: an anonymous caller can *execute* the staff functions `create_household`, `rename_*` and `delete_*`. They run their own validation and return application errors (400 "Household details are required", 400 "GKK not found", 204) instead of "permission denied". They are `security invoker`, so row-level security stops every write; the GKK list, the households and the draft were verified unchanged afterwards.
  Repro: `POST /rest/v1/rpc/delete_gkk {"target_name":"GKK Sto. Niño"}` with only the publishable key → 204, GKK still present.
  File: `supabase/migrations/0001_init.sql` (re-created in 0003, 0006, 0009): the `grant execute … to authenticated` lines are not paired with `revoke execute … from public, anon`, unlike migrations 0005, 0007 and 0010.
  → Suggestion: add a migration that revokes execute on those functions from `public, anon`, so the boundary no longer rests on RLS alone.
- **H2 — s-api-profiles-promote / -delete** — Symptom: a staff session's `PATCH` and `DELETE` on `profiles` are not refused with "permission denied" (200 `[]`) and an `INSERT` fails only with an RLS violation. So `authenticated` holds more table privileges than migration 0001 grants (`select` only). Safe today (`is_admin` stayed false; the admin profile survived), but RLS is the only barrier.
  File: Supabase default privileges on new tables; `0001_init.sql` grants.
  → Suggestion: add `revoke insert, update, delete on profiles from authenticated, anon;` in a migration.
